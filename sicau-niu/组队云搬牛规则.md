# 组队云搬牛规则

## 1. 规则结论

组队云搬牛采用“固定团关系 + 成员独立上报贡献”的模型，不再使用“队长开始全队会话、成员持续提交轨迹、队长结束全队会话”的搬运模型。

本玩法基于两次成功上报坐标之间的直线位移计算贡献，权威单位为米。该数值不是微信运动步数，也不能证明用户实际步行距离；小程序和管理后台统一展示为“贡献里程”或“贡献值”，不得展示为“微信步数”或“运动步数”。

## 2. 核心定义

| 名称 | 定义 |
|------|------|
| 本次活动 | 当前寻牛活动周期，是团历史和贡献历史的归档范围。 |
| 有效团 | 尚未失效的团。系统同时最多允许存在`120`个有效团。 |
| 无效团 | 连续`72`小时没有成员活跃后关闭的历史团，不在小程序展示，也不占用`120`个有效团名额。 |
| 团 | 活动期间创建的持久组队实体，使用稳定团 ID 区分。去除首尾空白后的团名在有效团中唯一；团失效后释放名称但保留历史记录，不物理删除。 |
| 创建者 | 成功创建团的用户。创建成功后自动成为该团成员，不具有独占贡献权限。 |
| 成员绑定 | 用户当前唯一的有效团关系。用户创建团也视为加入该团；原团失效并关闭绑定后，用户可以重新开团或加入其他有效团。 |
| 上报基准点 | 用户最近一次成功上报的位置；首次成功上报前不存在基准点。 |
| 每日上报次数 | 同一用户在北京时间同一自然日内首次成功受理的位置上报数量，与所在团无关，每日最多`12`次。 |
| 上报事实记录 | 每次首次成功受理的位置上报对应的一条数据库记录，是后续统计、审计和汇总校验的权威明细。 |
| 单次贡献 | 当前成功上报位置与上一个基准点之间的`GCJ-02`大圆直线距离，单位为米。 |
| 累计贡献 | 用户历次有效单次贡献之和；团累计贡献为团内全部成员有效贡献之和。 |

## 3. 创建团

1. 任何已登录且尚未绑定有效团的用户都可以创建团。
2. 创建团时必须提交团名。创建请求成功是创建者唯一一次面向用户端的命名机会；创建完成后，小程序不提供改名接口。
3. 去除首尾空白后的团名在全部有效团中必须唯一。若开团时名称已被有效团使用，服务端返回稳定的“有效团名已被使用”业务错误且不创建团或成员绑定。
4. 相同`requestId`的创建重试必须返回首次创建结果，不得重复创建团，也不得被视为第二次命名。
5. 创建成功后，创建者在同一事务内自动加入该团。因此，一个用户同一时间最多创建或加入一个有效团；原团失效后可以创建新团，并获得新团的一次命名机会。
6. 系统同时最多允许存在`120`个有效团。服务端必须先结算到期团，再原子校验有效团数量，确保不会出现第`121`个有效团。
7. 达到上限后，所有新建团请求都返回稳定的“有效团数量已达上限”业务错误；团自动失效后立即释放名额和团名。后台改名、隐藏展示或查看团信息不得释放名额。
8. 管理后台可以修改团名。后台改名必须经过宿主认证、权限校验并保留操作审计，不改变创建者的用户端命名次数；修改有效团时同样不得与其他有效团重名。
9. 有效团名唯一性必须由事务内校验和数据库部分唯一索引共同保证，并发创建或后台改名只能有一个同名有效团成功。无效团不参与唯一性约束，因此其名称可以被后续有效团再次使用。
10. 新活动周期是否开放以及历史团如何归档由运营流程控制；活动切换不得物理删除既有团、成员和上报事实记录。

## 4. 加入团

1. 每个用户同一时间有且只能绑定一个有效团；已创建或已加入有效团的用户不能再加入其他团。
2. 用户端不提供退出、换团或解散团能力。误入团等纠错场景不在本规则范围内，需要另行定义管理后台纠错流程。
3. 加入团没有地理位置、距离、人数或运动状态限制，不读取加入者或现有成员的位置。
4. 本期不设置团成员人数上限。成员列表必须分页或有界返回，服务端使用集合化查询装配，不得产生`N+1`查询。
5. 相同`requestId`的加入重试必须返回首次加入结果，不得重复建立成员关系。

## 5. 贡献上报

1. 团内所有成员都可以独立上报贡献，不区分创建者和普通成员，也不需要等待其他成员。
2. 上报请求必须包含当前位置、`requestId`和客户端采样时间；坐标统一使用`GCJ-02`。
3. 用户首次成功上报时，服务端保存上报基准点并写入一条起点为空、单次贡献为`0`米的上报事实记录，不增加用户或团累计贡献。
4. 用户后续每次成功上报时，服务端读取该用户上一个基准点，使用`Haversine`公式计算到当前位置的直线距离，并将结果按整数米四舍五入后计入贡献。
5. 一次成功上报必须在同一事务内完成上报事实记录写入、每日次数占用、用户累计值更新、团累计值更新、基准点推进和团最后活跃时间更新，任一步失败都不得产生部分结果。
6. 只有成功上报才能写入上报事实记录并推进基准点。参数错误、鉴权失败、未加入团、幂等冲突、超过每日上限或存储失败均不得改变基准点和累计贡献，也不得新增正常上报记录。
7. 相同用户使用相同`requestId`重试时，必须稳定返回首次上报的起点、终点、单次贡献、用户累计贡献和团累计贡献，不得重复写入上报事实记录或重复累计。
8. 团累计贡献等于该团全部上报事实记录中单次贡献之和；用户加入团之前不存在可归属贡献，不能补记到当前团。
9. 同一用户的并发上报必须由服务端串行化，并按事务成功提交顺序推进基准点。客户端采样时间只用于审计和异常判断，不能覆盖服务端确认的基准点顺序。
10. 每名用户每天最多成功上报`12`次位置。每日窗口按北京时间（`UTC+8`）自然日零点切分，不随服务器部署时区变化。
11. 每日次数按用户计数，与团和成员绑定无关。团失效后重新创建或加入其他团不会重置当日已用次数。
12. 首次建立基准点且贡献为`0`米的成功上报也占用`1`次并写入上报事实记录；后续成功受理但计算距离为`0`米的上报同样占用`1`次并写入记录。
13. 服务端必须先查询幂等结果，再对新的`requestId`校验每日次数。同一`requestId`的幂等重放只返回首次成功结果，不重复占用次数；即使首次成功后已达到每日上限，也不得把该重放误判为新的超限请求。参数错误、鉴权失败、未加入有效团、团已失效、存储失败和超过每日上限而被拒绝的请求均不占用次数。
14. 第`13`次及之后的首次请求必须返回稳定的“今日位置上报次数已用完”业务错误，并且不得写入上报事实记录、推进基准点、更新个人或团累计贡献、刷新团最后活跃时间。
15. 每日次数校验、次数占用和贡献事务必须按用户串行化，并由数据库约束或原子计数兜底，保证并发请求也不会产生第`13`次成功上报。
16. 每条上报事实记录至少保存稳定记录 ID、活动标识、团 ID、成员关系 ID、用户 ID、`requestId`、北京时间日键、可空起点经纬度、当前上报经纬度、客户端采样时间、服务端受理时间和本次贡献米数。日键必须按服务端受理时间换算，客户端时间不得改变限次归属日。
17. 同一用户和`requestId`必须具备数据库唯一约束。首次上报和后续距离为`0`米的成功上报都必须形成事实记录，不能因为没有新增贡献而省略。
18. 上报事实记录在团失效、成员绑定关闭或活动归档后继续保留，不得物理删除、跨团改写或被累计快照替代。个人和团累计值是事务内维护的读取快照，必须能够由事实记录重新汇总和校验。
19. 后续统计按用户、团、活动和北京时间日键等维度在数据库侧聚合。上报表至少为用户与日键、团与服务端受理时间等高频条件建立合适索引；明细查询必须分页，不得全量加载后在应用内统计。

## 6. 团活跃与自动失效

1. 创建团成功时，以服务端创建时间初始化团的最后活跃时间。
2. 团成员成功加入或成功上报贡献时，以服务端提交时间更新团的最后活跃时间。首次贡献上报虽然贡献为`0`米，仍属于有效活跃事件。
3. 后台改名、后台或小程序查看、失败请求、幂等重放和其他不产生新成员绑定或新上报事实记录的操作不得更新最后活跃时间。
4. 当服务端当前时间大于或等于团最后活跃时间加`72`小时时，团必须自动标记为无效。该时间窗是连续`72`小时，不按北京时间自然日取整，也不信任客户端时间。
5. 自动失效必须在同一事务内将团状态更新为无效、记录失效时间和失效原因，并关闭该团全部有效成员绑定。历史成员、上报事实记录和累计贡献必须保留，不得物理删除或归零。
6. 团失效后，小程序团列表、搜索、详情和加入接口均不得返回或接受该团；该团立即不再计入`120`个有效团上限，并释放团名供后续新团复用。
7. 被自动退出的用户可以重新创建或加入其他有效团。进入新团后，该用户没有上报基准点；在当日上报额度可用时，首次成功上报建立新团基准点、写入贡献为`0`米的上报事实记录。旧团最后上报点不得跨团参与计算；若当日`12`次已经用完，用户必须等到下一个北京时间自然日再建立新团基准点。
8. 服务端必须同时使用只在主节点执行、默认每`1min`运行一次的后台到期扫描，以及玩家请求事务内的到期兜底检查。创建团、加入团、上报贡献和读取小程序团列表时，即使后台扫描尚未执行，也必须先排除或结算已到期团，避免旧团继续可见或占用名额。
9. 失效与加入、上报并发时必须锁定团记录后按服务端时间判定：已经达到`72`小时的团先失效，临界请求不得续期或恢复该团；尚未达到阈值的成功加入或成功上报可以正常更新最后活跃时间。

## 7. 接口与展示闭环

1. 小程序不再提供“开始搬运”“记录轨迹”“结束搬运”和空闲超时交互，统一为“加入团”和“上报贡献”。
2. 团状态接口至少返回团 ID、团名、创建者、成员数量、团累计贡献、本人是否已绑定、本人的累计贡献、本人是否已有上报基准点、本人今日已用上报次数和剩余上报次数。
3. 上报成功响应直接返回本次贡献、最新个人和团累计贡献、今日已用次数及剩余次数，小程序不得通过额外请求自行推算。
4. 团列表最多包含当前`120`个有效团；成员明细使用独立分页接口，避免团列表携带无界成员数组。
5. 团成员只能看到其他成员的公开身份和贡献汇总，不得读取他人的原始上报坐标。上报事实记录中的原始坐标属于敏感业务数据，仅允许本人和具有审计权限的管理人员按授权范围分页读取；统计接口默认返回聚合结果，不得暴露可还原他人轨迹的明细。
6. 小程序不得展示、搜索或进入无效团。用户原团失效后，页面应恢复创建团和加入团入口，不得继续显示旧团为本人当前团。

## 8. 明确不包含的语义

- 不使用团成员之间的距离作为建团或入团条件。
- 不设置最低成团人数；单人团创建后即可开始上报贡献。
- 不存在队长启动、全队共享运动会话或队长结束全队活动。
- 不累计上报间的轨迹折线，只计算相邻两次成功上报点之间的直线距离。
- 不因退出现已失效的团或重新入团而重置用户当日上报次数。
- 不读取或换算微信运动步数。如后续需要真实步数，应独立接入微信运动授权与服务端解密流程。
